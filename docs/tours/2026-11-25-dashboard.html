Pulse dashboard tour

A tour of what issue #10 added: a page at /dashboard that maps the system and shows, live from Postgres, whether each sync is working, how many rows each table holds, how stock moves, and where Shopify and AX disagree. To make sync health visible, every sync run is now recorded. Every number on this page comes from a real run on 25 November 2026.

What it looks like

The live page after the first sync, at 13:57 on 25 November. Each box on the map opens its details on the right. Lines take the colour of the sync that feeds them. MCP is drawn dashed because #9 hasn't built it yet.

Where it sits

A read-only page on top of Postgres

The dashboard never talks to AX or Shopify. It reads what the syncs wrote, plus a new ops.sync_runs table that the workers fill. A source that can't be reached shows up as a failed run, with its error.

Step through it

From a sync run to a green dot

  1. Each sync reports what it wrote

    ISync now has a Source name and RunAsync returns rows written per table. AX counts what each COPY imported, and Shopify counts its inserts.

    src/Pulse.Api/Sync/SyncWorker.cs:8 · Ax/AxSync.cs:48 · Shopify/ShopifySync.cs:80

  2. The worker records every run, good or bad

    RunOnceAsync times the run, catches a failure as before, then inserts one row into ops.sync_runs: start, end, ok, the error's type and message, and the row counts as JSON. If even that insert fails (Postgres down), it's logged and the worker carries on.

    SyncWorker.cs:34 · insert at :54 · table in src/Pulse.Api/Ops/ops.sql

  3. The data source is always registered

    The Postgres data source and clock used to exist only with sync on. The dashboard needs them too, so they're registered in all cases. That means the page also works with Sync:Enabled=false.

    src/Pulse.Api/Program.cs:15 · dashboard mapped at :56

  4. One endpoint for the whole page

    /dashboard/data?range=7d[&sku=X] loads everything on screen in one call. It's internal to the page; Claude will read through MCP instead.

    src/Pulse.Api/Dashboard/DashboardEndpoints.cs:14 · DashboardData.cs:25

  5. Status comes from the last run

    OK: the last run worked within 30 minutes (two intervals). Stale: it worked, but longer ago. Failing: the last run failed. No runs yet, or Off when Shopify has no credentials, in which case the panel shows the user-secrets commands. Colour always comes with a word and a shape.

    DashboardData.cs:46

  6. Gaps compare the warehouse, on hand

    For each SKU in both systems, AX's on-hand stock at LAGER is compared with Shopify's. The location is set in appsettings.json under Dashboard:Warehouse. Gap = Shopify − AX, largest first. Available stock is shown alongside but not compared, because each side subtracts its own reservations.

    DashboardData.cs:119

  7. The chart uses the same measure

    Warehouse on hand per sync over 24 hours, 7 days or 30 days, summed for all SKUs or, after you click a gap row, for one SKU. Every table and view in raw_ax, raw_shopify, core and ops gets an exact count(*).

    DashboardData.cs:188 · :93

No stock gaps

All 30 SKUs have the same on-hand count at AX LAGER (523 in total) as in Shopify. Six snapshots per source so far today; the chart lines lie on top of each other.

The first formula flagged 20 of 30

Comparing available stock summed over all AX locations counted the 28 items in the shop (BUTIK) and each side's own reservations as gaps. With LAGER only it was still 9 of 30. Hence on hand at the warehouse.

The live store has no orders

raw_shopify.orders is empty on the dev store; the 2 Shopify orders in the core tour came from the test recordings. Anything about webshop sales needs test orders in the store first.

Run it yourself

Try it on your machine

Start Postgres and the AX emulator, then the API: 
docker compose up -d
dotnet run --project src/Pulse.Api
Open the dashboard: 
xdg-open http://localhost:5017/dashboard
The runs behind the status dots: 
docker exec pulse-postgres-1 psql -U pulse -d pulse -c "SELECT source, started_at, ok, error, rows_written FROM ops.sync_runs ORDER BY started_at DESC LIMIT 6;"

Tests

The worker tests use their own Postgres container. The dashboard tests share the core tour's lab: AX seeded, both syncs run, views created; changes are rolled back.

  • No_gaps_when_the_warehouse_agrees_even_though_ax_has_shop_stock_tooBUTIK stock doesn't count as a gap.

Decisions for you

Now

Commit on dashboard, then merge into phase-1-lab. #9 will touch Program.cs too, so merge before it starts or expect a small conflict.

After #9

Turn the dashed MCP box into a live one: is /mcp up, and which tools does it have.

Sync now

A button to run a sync right after reseeding was left out to keep the page read-only. Its own issue if you want it.

Two APIs

Two copies of Pulse.Api running at once (say, one per worktree) both sync into the same Postgres, so you get twice the snapshots. Fine in the lab, but run just one.
